# 按意思找代码

一个工具，叫 `recall`：给它一个问题，它给出最像的几段代码，带上出处。

```
recall {"query": "会话是在哪里写到磁盘上的", "k": 5}
1.000  src/main/java/com/ccj/agent/session/FileSession.java:88-104
    ...（那一段）
```

它补的是 `grep` 补不上的那个缺口。`grep` 找字：它只在**你已经知道要找的东西叫什么**的时候有用——而在一个
陌生的仓库里，那正是你不知道的事。`recall` 找意思：「会话是在哪里写到磁盘上的」与「每一条消息之后追加一行
并 flush」之间没有一个共同的词，而它们说的是同一件事。

## 它是**有条件**出现的

它在工具表里出现，当且仅当应用主目录下有一份 `embeddings.json`：

```json
{
  "baseUrl": "http://127.0.0.1:1234/v1",
  "model": "nomic-embed-text",
  "apiKeyEnv": "OPENAI_API_KEY",
  "chunkLines": 40,
  "overlapLines": 8
}
```

`/v1/embeddings` 是这个仓库只讲的一种协议，因为它是这一行事实上通用的那一种：OpenAI、Azure、OpenRouter、
Ollama 的 `/v1`、vLLM、llama.cpp、LM Studio 都讲它。所以「用本机的一个小模型算向量」不需要任何新的适配器，
也不需要把代码发到任何地方去——把 `baseUrl` 指向 `127.0.0.1` 就什么都不出这台机器。

没有这份文件时，`recall` 根本不在工具表里。这与这个仓库对搜索的一贯立场一致（核心不带搜索，是因为它要一把
第三方密钥与一个供应商选择），而这里多出来的一条是：**本机的嵌入模型让「本地优先」这件事仍然成立**。

## 它把文字送出去，所以它先问

`recall` 是这个代理里唯一一个把工作目录里的**文字**送给别人的东西，所以它是唯一一个审批提示里带着数字的工具：

```
批准 recall — 把工作目录里 128 个块的文字发给 nomic-embed-text（http://127.0.0.1:1234/v1/embeddings，
每块 40 行，重叠 8）算向量（索引在 ~/.oh-my-ccj/index/3f1a…），然后按意思检索？[y/N/s/a/d]

（块数、端点、索引目录都是当场算出来的；上面的 128 只是个例子。）
```

于是「要不要用检索」这个问题，在这里变成了一个可以被回答的具体问题：**有多少文字，去哪里。**

一次**没有改动**的检索谁都不问：块的内容没变，指纹没变，向量已经在索引里了，于是没有任何东西要离开这台
机器——没有出口，就没有问题。这也是为什么「增量的索引」在这里不只是省钱：它同时让绝大多数检索不必打扰人。
实测：第一次构建之后，一个没有改动的语料再索引一次**一个块的文字都不发**（`RetrievalIndexTest` 钉住
`requests()` 不变），一次检索只发出去**那一句查询**——`RecallToolTest` 数的是替身端点收到的文字段数，第二次
调用恰好比第一次多一。

## 索引

放在 `<home>/index/<工作目录的绝对路径的散列>/`，与仓库分开：它是缓存，而缓存不该出现在 `git status` 里。

| 文件 | 是什么 |
|---|---|
| `meta.json` | 这份索引是哪个端点、哪个模型、哪种切块方式建的 |
| `chunks.jsonl` | 一行一个块：路径、起止行号、指纹、正文 |
| `vectors.bin` | 按同一顺序紧排的 32 位浮点数，写进去之前已经归一化 |

三件事值得写下来：

- **换模型就是整份重建。** 两个模型的向量不在同一个空间里，而那个空间里的点积**不会报错**——它只会给出一个
  没有意义的相似度。所以 `meta.json` 一旦对不上，索引按空的算。
- **指纹算的是内容加位置。** 改一个文件只重算它改动了的那几块，这是「重新索引一个仓库要花多少钱」的全部
  依据。实测（三份文件的语料，改其中一份）：只有它自己那一块被重算，其余命中缓存。
- **正文也留在索引里。** 只存行号会让每一段结果都要回去把文件重读一遍，而那些行在两次检索之间可能已经变了
  ——「你找到的那一段」与「它给你看的那一段」于是不再是同一段。

## 搜索是暴力的，这是量出来的决定

每个向量与查询算一次点积，取前 k 个。没有近似索引（HNSW 那一类），因为在这个规模上不值得：

- 语料是**几千个块**量级（一次索引读的源码有 16 MiB 的上限），每次搜索是几十万次浮点乘加，本机上是毫秒级；
- 近似索引要用一次「可能漏掉真正最近的那个」换一次快。在几千个块上，那次快换来的是几十微秒，而漏掉的那个
  换来的是一句「检索不准」。

等语料涨到几十万块，这里会先变成一个**能被测量**的瓶颈，再被换掉——在那之前，暴力搜索是一个正确的答案，
而不是一个偷懒的答案。

## 检索质量

它被量过，而数字在这里：一个本地替身端点、二十份各讲一件事的文件、十句只与其中一份共享词的问题（整句原样
不出现在任何文件里，所以这是检索而不是 grep）：

```
检索质量（20 份文件，20 个块）：recall@1=0.90  recall@5=1.00  MRR=0.95
```

这组数字由 `RetrievalIndexTest.recallAtKIsMeasuredAgainstPlantedFacts` 打印并断言（`recall@5 = 1.0`、
`MRR > 0.6`）。它量的是**这一套东西**——切块、指纹、缓存、归一化、排序——而不是哪个模型有多聪明：替身的向量
是词袋散列加双词，它不懂同义（把 `stored` 与 `storage` 当成两个词），所以那些问句用的是语料自己的词汇。
换成一个真的嵌入端点会换掉那些向量，不会换掉这段代码。

诚实的那一半：**这个仓库里没有一个数字来自真实的嵌入模型。** 本机上能跑通的只有替身端点，所以「换一个真
模型之后召回率是多少」是一句没有被验证过的话——见 ROADMAP 里这一项的状态。

## 限制

- **一次索引是一个采样。** 一次构建最多读 16 MiB 的源码、单个文件不超过 512 KiB、最多两万个块。更大仓库的
  代价不是一次崩溃，而是一个不完整的索引——而那意味着「检索没找到」有时等于「它没被索引」。
- **它不是搜索。** 没有网页、没有新闻、没有仓库之外的东西：它只索引这个工作目录里的文字。
- **它只在 `read` 能读的文本上工作**：二进制被跳过，`target/`、`.git/`、`node_modules/`、`.idea/` 与
  `glob`/`grep` 一样被跳过——一个把编译产物也索引进去的检索工具，会用生成物回答关于源码的问题。
