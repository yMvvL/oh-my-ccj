# 这个工具自己有多贵

三笔会被用户感觉到的开销，以及量它们的方法。它们不是估算——三项都是在一台真机器上跑出来的墙钟时间，
而产生它们的代码就在 [`src/test/java/com/ccj/agent/perf/OverheadLedger.java`](../src/test/java/com/ccj/agent/perf/OverheadLedger.java)
里，`OverheadLedgerTest` 守着它们不悄悄变坏。

理由很简单：「小到能读完」是这个项目的卖点之一，而小如果不体现在延迟上，就只是一种审美。一个不到三千行的
核心，如果启动要两秒、每个回合先白付四千 token，那么它和上面那些三十万行的东西之间的差别就只剩行数。

## 怎么量

```bash
./mvnw -o -Dtest=OverheadLedgerTest test        # 三个数字都打印在输出里，也各有一条宽松的上界
```

三个数字的量法各自不同，因为它们的性质不同：

| 数字 | 怎么量 |
|---|---|
| **启动** | 起一个**真的子进程**：`java -cp <本进程的类路径> com.ccj.agent.cli.Main <flag>`，从 `ProcessBuilder.start()` 到 `waitFor()` 返回。两次启动之间的差值是配置与工具注册表的代价。取三次里最好的一次（抖动的方向只有一个）。 |
| **每回合的前缀** | 确定性的估算，不需要跑任何东西：`Prompts.system(null, null)` 加上 `Tools.standard().specs()` 里每个工具的名字、描述与手写 schema，各自过一遍 `TokenEstimate`——与上下文预算用的是同一个启发式。 |
| **列一次会话** | 在临时目录里造一个 2 MiB / 2715 条消息的会话文件（一条用户消息，加一串助手回合与它们的大块工具输出），然后计时 `SessionStore.list`。**预热用的是另一个目录**：本 JVM 里第一次解码几兆字节的会话要花一百多毫秒，而那主要是 JIT 还没把 Jackson 那条路编译出来；在同一个目录上列两次，第二次又命中索引缓存，于是要量的那次落空就没了。 |

## 本机量到的数字

Temurin 21.0.11、Linux 7.2.9-arch1-1 x86_64、一次典型的桌面负载（2026-10-11）：

| 开销 | 数字 |
|---|---|
| 进程启动 → 打印版本退出（JVM 底价） | **54 ms** |
| 进程启动 → 工具表建好、可以收下第一条消息（`--tools`） | **574 ms** |
| 每个回合固定重发的前缀 | **1908 token**，其中系统提示 245、工具 schema 1663（8 个工具，6638 字符） |
| 列一次会话目录，缓存落空（2 MiB / 2715 条消息） | **21 ms** |
| 同一个会话，缓存命中 | **0 ms** |

三句话解释这张表：

- **启动的五百毫秒里，JVM 只占五十。** 剩下那五百毫秒是配置叠加、工作区注册表、以及十四个工具类的加载与
  它们手写 schema 的生成。对一个常驻进程（web UI、REPL）这笔钱只付一次，对 `-p` 那种一次性运行它占的
  比例就很大——这正是它值得被记在这里的原因，而不是因为它大。
- **每个回合先花掉将近两千 token 的工具说明。** schema 比系统提示大将近七倍，而它们每个回合都原样重发。
  Anthropic 那条路上有三个 `cache_control` 断点（系统、工具集、对话末尾），所以重复的部分按缓存读取计价
  ——但缓存是提供方的优惠，不是把前缀缩小的替代品：数一数它要花多少，是唯一会让人去缩它的东西。所以
  `ccj --tools` 现在把每个工具的估算 token 与合计一起打印出来。
- **一次会话列表是二十毫秒，不是一次停顿。** 它之所以是二十毫秒而不是两百，就是因为
  `SessionIndex` 按（修改时间，大小）缓存：没动过的会话一次都不被重新推导（命中是 0 ms），动过的那个
  每个回合付一次这一笔。

## 什么**没有**量

诚实地说清楚，因为一个没写条件的数字会在别人的机器上变成一句假话：

- **CI 上的数字**。这张表来自维护者的机器；CI 的 Linux 与 macOS 跑的是同一套用例，边界留得比本机数字宽
  几十倍——它们防的是一次数量级的恶化，不是一次百分之十的抖动。
- **macOS 与 Windows**。启动那两行在 macOS 上会不一样（JVM 与文件系统的差别），而 Windows 在这个项目里
  整体上还没有被验证过。
- **web UI 就绪**、**一次真模型回合的时延**（那取决于提供方，不取决于这里），以及**内存占用**——一条
  `-Xmx` 曲线不是今天要回答的问题。
- **jar 与 classes 的差别**。表里的进程用的是 `target/classes`，用户拿到的是 2.9 MB 的 fat jar；类由同一个
  类加载器从同一个位置读，只换了一个压缩容器，所以这个差别没有被量出来，也不该被当成零。

## 一个被否掉的优化，连同它的测量

路线图（4.5）原来写着要修：**「侧栏每次列会话都会把变更过的会话文件整个解码，而它只需要第一行」**。

量出来的答案是：这件事**不值得做**。列一个 4 MiB 的会话，全解码是十五毫秒；如果改成「只解标题那一行、
其余只数行数」，是四到六毫秒——省下十毫秒，代价是丢掉「损坏的会话文件在列表里就以损坏的样子出现」这条
性质（[`oneDamagedFileDoesNotHideTheSessionsBesideIt`](../src/test/java/com/ccj/agent/session/SessionStoreTest.java)
钉着它）。十毫秒在一条以秒计的回合里是噪声，而那条性质是用户看得见的。

真正让这个数字变小的是**缓存**，而它早就在了：没动过的会话不会被重新推导（命中 0 ms）。所以这一项以
「量过、否掉、把代价写在下面」结束，而不是以一次改动结束。哪一天单条会话长到几十兆字节，这条测量会跟着
它的输入一起过时——那时候重做的第一件事是重新量，而不是照着一份两年前的结论动手。
